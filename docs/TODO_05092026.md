# TODO · Arquitectura de datos y audio

Fecha: 2026-09-05

## Contexto actual

Lynx Platform es el catálogo y back-office musical de ODR. Gestiona tracks,
metadatos técnicos, derechos, usuarios, solicitudes de licencia, playlists y
servicios de audio.

La arquitectura actual es sólida y se mantiene vigente:

| Área | Implementación actual | Evaluación |
| --- | --- | --- |
| Datos, usuarios, derechos y licencias | Supabase Postgres + Prisma | Adecuada |
| Audio y otros assets | Cloudflare R2 con API compatible con S3 | Adecuada |
| Carga de archivos | URLs firmadas de corta duración | Buen patrón |
| Análisis técnico | FFmpeg y FFprobe | Estándar profesional |
| Aplicación | Next.js + TypeScript | Adecuada |

No se recomienda reemplazar Supabase, R2 o Prisma por otra plataforma sin una
necesidad concreta. La evolución debe fortalecer seguridad, escalabilidad y
separación de assets.

## Prioridad 1 · Proteger la firma de cargas

Estado actual: `src/app/api/uploads/sign/route.ts` genera URLs firmadas para
subir a R2, pero no valida una sesión ni un rol. El middleware actual solo
protege `/admin/**` y `/creator/**`, no las rutas `/api/**`.

Riesgo: si el endpoint queda accesible públicamente, un tercero podría pedir
una URL firmada y subir archivos dentro de los límites configurados.

Acciones:

- [ ] Requerir un usuario autenticado en `POST /api/uploads/sign`.
- [ ] Permitir la firma solo a roles `ADMIN` o `STAFF`.
- [ ] No aceptar `dir` libremente desde el navegador; usar una lista cerrada de
      directorios permitidos en servidor.
- [ ] Conservar límite de tamaño, tipos MIME permitidos y expiración breve.
- [ ] Registrar usuario, key, tamaño, MIME y fecha para auditoría.

## Prioridad 2 · Separar audio público y privado

Usar al menos dos categorías de assets:

| Tipo | Acceso recomendado | Ejemplos |
| --- | --- | --- |
| Público | URL de CDN/dominio personalizado | previews MP3/OGG, portadas, waveforms |
| Privado | URL firmada tras validar permiso/licencia | masters WAV, stems, descargas de cliente |

Acciones:

- [ ] Mantener el master original privado.
- [ ] Generar un preview comprimido para el reproductor público.
- [ ] Entregar stems y masters con URLs firmadas de duración breve.
- [ ] Configurar un dominio personalizado para R2 en producción, en vez de usar
      `r2.dev`.
- [ ] Aplicar caché y reglas de acceso/WAF al dominio de assets públicos.

Referencia: https://developers.cloudflare.com/r2/buckets/public-buckets/

## Prioridad 3 · Procesamiento de audio en segundo plano

Estado actual: el análisis de un track descarga audio, ejecuta FFprobe/FFmpeg,
mide LUFS/LRA/True Peak, genera waveform y escribe los resultados en la base de
datos dentro de una petición HTTP.

Riesgo: archivos largos o muchas tareas concurrentes pueden exceder tiempos de
espera y afectar la respuesta del panel de administración.

Arquitectura objetivo:

1. El admin sube el archivo a R2 y se crea/actualiza el track en Postgres con
   estado `PENDING`.
2. La aplicación publica un trabajo de análisis en una cola.
3. Un worker con FFmpeg descarga el asset, genera métricas, waveform y preview.
4. El worker sube derivados a R2 y actualiza el estado a `READY` o `FAILED`.
5. La UI muestra progreso y permite reintentar errores.

Acciones:

- [ ] Crear estados de procesamiento y campos de error/reintento en la base.
- [ ] Incorporar una cola y un worker con capacidad de ejecutar FFmpeg.
- [ ] Hacer las tareas idempotentes para evitar duplicados al reintentar.
- [ ] Añadir observabilidad: duración, logs, intentos y alertas de fallos.

Referencia: https://developers.cloudflare.com/queues/get-started/

## Prioridad 4 · Cargas grandes y reanudables

La carga actual con un `PUT` firmado es apropiada para archivos pequeños o
medianos. Para masters WAV grandes conviene incorporar carga multipart y
reanudable.

Acciones:

- [ ] Definir un umbral de tamaño para usar multipart.
- [ ] Permitir reanudar una subida interrumpida.
- [ ] Verificar integridad con checksum/ETag y guardar tamaño final.
- [ ] Configurar limpieza de cargas multipart incompletas.

Referencia: https://developers.cloudflare.com/r2/objects/upload-objects/

## Modelo de derivados recomendado por track

- Original/master: privado, sin reproducción pública.
- Preview: MP3 u OGG optimizado, público mediante CDN.
- Waveform: JSON pequeño, público junto al preview.
- Metadatos: duración, sample rate, canales, bitrate, LUFS, LRA y True Peak en
  Postgres.
- Stems y entregables: privados, disponibles solo tras validar el acceso.

## Supabase y R2

Supabase se usa para Postgres a través de Prisma. La aplicación no depende de
Supabase Auth ni Supabase Storage para este flujo. R2/S3 es el storage de
assets de audio.

Variables que deben permanecer solo en `.env.local` o en secretos del entorno
de despliegue:

- `DATABASE_URL`
- `DIRECT_URL`
- `S3_ENDPOINT`
- `S3_BUCKET`
- `S3_ACCESS_KEY_ID`
- `S3_SECRET_ACCESS_KEY`
- `S3_PUBLIC_BASE_URL`
- secretos de sesión y administración

Nunca versionar ni pegar estos valores en documentación, commits o chat.
